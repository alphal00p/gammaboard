# Campaign 55: sampler recovery loop and stale running statuses

Investigated on September 24, 2026, approximately 10:46–10:52 UTC against the
deployment on PostgreSQL port 5400 and API port 4000. Database and API inspection
was read-only. No assignments, checkpoints, tasks, or deployment processes were
changed. A standalone Rust diagnostic reproduced the comparison against exported
checkpoints without connecting to the live database.

## The stall is a false checkpoint conflict

Campaign `epem-a-ttxh-NLO-madnis-campaign` (55), controller task 157, selects only
GL00 (run 56, sample task 160). Its configuration has `max_active_runs = 1`.
There are 70 live evaluators assigned to GL00 and one live sampler, `local-632`.
The sampler has no active role: its activity remains `initializing runtime`.

Every roughly 6–7 seconds, the worker logs:

> runtime state changed during role activation; retrying

with the error `recovery checkpoint changed during runtime initialization`.
There were 158 such messages for run 56 between 10:31:50 and 10:51:30 UTC,
spanning the previous worker deployment and the current one.

The checkpoint has actually remained unchanged: `updated_at` is
`2026-09-24 09:45:56.367406+00` and its database JSON-text MD5 is
`7ed29a3037ee1592ba4b15aa53bef4d1` in repeated observations.

The guard in [recovery.rs](../../src/stores/recovery.rs) compares raw database
JSON with `serde_json::to_value` of the decoded `SamplerAggregatorCheckpoint`.
These two representations differ in exactly two places under
`observable_state.estimate.components[1].state.discrete_bins["0,0"].state.max_weighted_positive_point`:

- `parameterization_jacobian`
- `weight_factors[1].value`

In both places the saved JSON number is `7553746958286027000`, whereas the typed
`f64` field serializes as `7.553746958286027e+18`. PostgreSQL considers these JSONB
numbers equal. `serde_json::Value` considers the integer and floating-point
representations different. Nothing needs to change in the database for this
guard to fail forever.

The raw comparison predates our recent changes: blame attributes it to commit
`fc0fcea2` (September 11), with the retry-activation classification added in
`24efb408` (September 17). This is a defect in that comparison, not a newly lost evaluator claim.
Decoding and re-encoding both sides through the same checkpoint type makes the
exported checkpoint compare equal. Testing all 11 current child checkpoints
found this raw-versus-typed mismatch only for GL00.
The same normalized comparison still rejects a deliberately changed completed
sample count in the standalone diagnostic.

Activation retry errors bypass the ordinary three-failure limit in
[node_runner/mod.rs](../../src/runners/node_runner/mod.rs). Each retry rebuilds
the evaluator metadata and Python sampler before reaching this comparison, so
the sampler repeatedly initializes but never begins ingesting results.

### Queue and database checks

- GL00's checkpoint records 50,425,626 produced and 50,279,936 completed samples
  for task 160: exactly 145,690 samples outstanding.
- The database retains exactly 101 completed batches containing those 145,690
  samples; all 101 have stored results. There are no pending, claimed, or failed
  batches for GL00. The recovery sample-count invariant is satisfied.
- The evaluators have no further work because the sampler cannot start and
  produce more work. Reallocating evaluators will not resolve this failure.
- PostgreSQL had 311 client connections against `max_connections = 512`; this
  observation does not indicate connection-limit exhaustion.

### Recommended recovery fix

Normalize the saved JSON through `SamplerAggregatorCheckpoint` before comparing
it with the already-decoded checkpoint, keeping the row lock and conflict check.
Do not remove the guard or introduce approximate numeric comparisons. A database
checkpoint revision carried from load to restore would be a stronger long-term
alternative that also detects replacement with semantically identical content.

Regression coverage should persist a large Jacobian through PostgreSQL JSONB,
verify that the untouched checkpoint restores, and verify that genuinely changed
progress or sampler state is still rejected. After this fix, GL00 should resume
from its existing checkpoint and ingest its retained results; the observed queue
does not require discarding samples or retraining.

## Extra running children come from expired node assignments

The run-list API reports GL00, GL06, GL20, and GL26 as `running`. Their desired
assignments at 10:50 UTC were:

| Child | Run | Stored assignments | Assignments with a live lease |
| --- | ---: | ---: | ---: |
| GL00 | 56 | 142 | 71 |
| GL06 | 58 | 71 | 0 |
| GL20 | 63 | 26 | 0 |
| GL26 | 65 | 41 | 0 |

`RUN_ASSIGNMENT_STATS_SUBQUERY` in [read.rs](../../src/stores/queries/read.rs)
counts desired and active assignments without checking `lease_expires_at`.
Any desired assignment makes the lifecycle `running`, including assignments of
workers from previous deployments. By contrast, `list_nodes` filters expired
leases, explaining why Node Management does not show these workers.

The campaign sub-run panel is already more accurate about selection: its API
returns GL00 as `running` and the other ten children as `waiting`. The separate
`running_children = 11` controller field counts unfinished/active child task
queues, not workers or concurrent execution. It should be renamed or recomputed
if presented as an execution count. GL00's panel label also reflects selection,
not successful sampler startup; it would be clearer to show `starting` while
there is no active sampler.

### Recommended status fix

Use live leases when counting assignments for lifecycle display, including the
active-worker count. Keep expired rows available for worker history and restart
intent; deleting them is unnecessary for this display fix. Add coverage for an
expired assigned worker beside a live worker and for a selected child whose
sampler is still initializing.

The [read-only SQL diagnostics](2026-09-24-campaign55.sql) capture the controller,
worker leases, queue, checkpoint identity, and retry log evidence. Exported
checkpoints and standalone reproduction output are under
`/tmp/gammaboard-ttxh-dev/campaign-55-*` in the investigation environment.

## Implemented fixes

Recovery now decodes the locked database checkpoint through
`SamplerAggregatorCheckpoint` before comparing it with the loaded checkpoint.
This accepts the unchanged large-Jacobian checkpoint while retaining the exact
state comparison, row lock, and queued-sample consistency check.

Run lifecycle queries now exclude expired leases from both desired-assignment
and active-worker counts. This also fixes the totals propagated to parent
campaigns, without removing worker history. Campaign Sub-runs consults live
sampler assignments: a selected child is `starting` while its sampler initializes,
`running` once the sampler is active, and `waiting` without a live sampler.

Regression tests reproduce both failures against an isolated PostgreSQL instance.
The checkpoint test uses the actual Jacobian above, checks that retained results
survive recovery, and verifies that changed progress and sampler state still
trigger a retry. The lifecycle test covers expired and live workers, draining
workers, parent aggregation, the run-list query, and preservation of worker
history. A panel unit test distinguishes an initializing sampler from an active
evaluator or sampler.

Validation passed: all 30 PostgreSQL integration tests, 296 library tests (one
unrelated test ignored), the full-stack campaign recovery test that replaces lost
sampler and evaluator workers, and Clippy with warnings denied. The PostgreSQL
tests used port 55439, separate from the live deployment on port 5400.

The fixes require redeploying the server and workers. There is no schema migration
or manual checkpoint repair. The live campaign and its retained results were not
modified during implementation or testing.
