# Ops consolidation validation — 2026-10-15

The UBELIX launcher now scopes jobs to a recorded workspace/offset deployment,
pins images and launcher/config snapshots, records leased per-worker submission
intent/receipts, and reconciles uncertain outcomes through Slurm/accounting.
Shutdown uses the same slot lock and cancels only owned jobs. Managed sync removes
obsolete files while preserving private configuration and runtime data. Builds
isolate sources/targets/staging, pin container bases, and require smoke success
before publishing immutable images. Resource normalization lives in Rust; both
launchers consume the canonical capabilities.

All schema changes, including campaign reservations and launch/build fencing, are
merged into `202610080001_initial_schema.sql`. Database model 2 requires a fresh
database. Checkpoints retain model 1. No incremental upgrade or flat external
launch-request compatibility path remains.

preservation of private configuration, deployments, images and resource data.

builds, premature success, changed job IDs and concurrent cohort replacement.

stranded-worker shutdown and watcher/shutdown interleaving. A historical launch

contract. The unrelated running demo was preserved.

## Remaining validation limits

- No real UBELIX allocation, accounting retention/outage exercise, GPU passthrough,
  or complete service-image compilation was performed in this environment. The
  mandatory publication smoke runs on the actual build host; until it passes,
  the new pipeline has not produced a verified release image.
- The pinned base images and lockfiles fix major inputs, but apt repositories and
  native dependency build scripts are not byte-for-byte reproducibility guarantees.
  Runtime package/compiler inventories remain in each image.
- Slurm and PostgreSQL cannot commit atomically. Unknown submissions intentionally
  require operator resolution. An incorrect `--not-submitted` assertion can still
  cause duplicate allocation; missing accounting alone is insufficient evidence.
- Filesystem locking assumes the shared workspace supports working advisory locks
  and atomic rename. Image/config hashes catch accidental edits; administrators
  with database/filesystem access remain trusted.

Operator behavior and repair commands are documented in the
[UBELIX guide](../../ops/ubelix/README.md); API states and identity fencing are in
[the external launch contract](../cluster-launches.md).
